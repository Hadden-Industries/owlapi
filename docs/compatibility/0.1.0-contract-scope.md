# Contract scope on the route to 0.1.0

This document reconciles implemented source contracts; it does not freeze or qualify a release candidate.
The [generated member delta](0.1.0-api-delta.md) compares published rc.2 source with the current authoritative registry, including inherited library methods and every member's performance disposition.

## Additions since published rc.2

The new exports are `NodeDocumentLoader` under the explicit Node-only `io/node` subpath and `ChangeApplied` under `model/parameters`.
The new methods on existing exports are profile accessors on `OWLDataFactory`, `OWLOntologyManager`, `OWLOntologyLoaderConfiguration`, `OWLOntologyWriterConfiguration` and the Manchester renderer; the manager's loader configuration getter/setter; and the loader's native configuration getters/setters listed in the generated delta.
No public binding was removed.
Inherited IRI and RDF/XML-format methods were already implemented; their newly complete inventory is a documentation correction.
The new subpath/exports target 0.1.0 for their first public release; rc.2 in the working package manifest must not be mistaken for publication of later source.

The [behavior profiles](behavior-profiles.md) define the meaningful compatibility changes beyond member names.
Omitted selection retains `normative-v1`; `java-owlapi-5.5.1` is explicit and immutable.
Unknown identifiers and mixed-profile use reject at their documented boundaries.
Both profiles keep the same declared package exports, while return values, defaults, ownership, partial mutation effects, resource limits and error timing may differ.
Java mutation returns `ChangeApplied`; normative mutation retains its boolean adaptation.
Java changed writer copies reset indentation/banners and preserve labels-as-banner; normative copies preserve unrelated fields.
Loader settings are captured before asynchronous acquisition, so later manager changes cannot alter a suspended operation.

The Node adapter requires application-owned authorization for each access operation and destination; receiving it does not grant ambient network/file access.
Its `load()` resolves to a `StringDocumentSource`, and authorization, native transport, decoding, resource and cancellation failures retain their owning contracts.
Portable parsing remains available; browser parity for the Node transport is not claimed.
Host restrictions, fresh public collections, source order, deferred reads, and documented Java omissions are part of compatibility, not optimization opportunities.

## Release-target metadata

Registry schema 2 names the field `firstPublicReleaseTarget` to make its historical planning meaning explicit.
Commit `7791b8a0` introduced the merger/provider with target `0.2.0` for a planned release; later changes retargeted them to `0.1.0-rc.1` before publication.
Commit `e27bcfea` introduced the publication preflight's requirement for an assigned first-release version.
The former name `firstPublicRelease` therefore never established that a release had occurred; historical alpha targets also demonstrate this distinction.
`null` means no target has been assigned, not that the implementation is unpublished.

Public release means an explicitly versioned release made available through the public npm registry or GitHub releases, including prereleases.
Code merely being readable on a moving branch does not establish a released version.
Actual availability comes from the release and registry artifacts, not this planning field or the development manifest.
Existing targets are retained on successful publication; there is no post-publication rewrite of the registry or generated views.
The generator owns one `ROADMAP_PUBLIC_RELEASE_TARGET` for the additions since published rc.2, currently `0.1.0`.
If the owner chooses an intervening prerelease, update that one input and regenerate before freezing its source and package; do not edit every row or mutate published artifacts.
This target is not a candidate selection, qualification result or release authorization.
Historical artifacts keep their original schema; comparisons normalize the old key when reading them.

This separates planned targeting from historical introduction conventions such as [JSDoc's `@since`](https://jsdoc.app/tags-since).
It also follows the principle behind [CPython's upcoming-release marker](https://discuss.python.org/t/versionadded-next/65280): resolve shared version intent through tooling rather than manually editing every document at publication time.

## OWL profile source assessment

`OWL2DLProfile.checkOntology()` assesses a captured structural import closure asynchronously and returns an immutable `OWLProfileReport`.
The formal verdict and optional retained-source assessment are separate: `sourceAssessment: true` does not redefine formal structural membership.
The retained source pass considers original RDF/RDFS structure and parsed expressions before consumer filtering.
Only trusted original arity and unambiguous typed use can support the two documented normalization/declaration qualifications.
Mutation invalidates the relevant source evidence; unsupported or incomplete work stays unverified.
Resource exhaustion makes `isInProfile()` throw `ResourceLimitError`, rather than treating an undetermined ontology as invalid.

This bounded implemented contract is exercised by `profiles/owl2DLProfile.test.js`, source-preservation/property-role tests and the datatype/profile suites named in the registry.
It does not implement every broader Phase 23 ambition or certify complete source preservation, arbitrary external vocabularies, inference or the full Java violation hierarchy.
The capability `profiles.owl2-dl-source-assessment` and its affected bindings therefore remain `IN_PROGRESS`; their existing release hold is preserved.
DEC-006 still requires the owner to settle any changed stable-release promise at surface freeze, which is outside this implementation's release authority.
No automatic completion marker or new full-validation claim is introduced here.

## Performance and release interpretation

The generated inventory matches exact member symbols to existing grouped workloads and exposes members with functional-only coverage and no individual timing claim.
Grouped or checksum-only measurements do not prove every overload or full semantic parity.
Each selected comparable group still needs admitted useful-work semantics and separate results for both profiles against the unchanged 1.10 target.
Extra normative work, measurement limits and remaining gaps require explicit dispositions; neither a fast checksum nor a passing structural API test substitutes for that decision.
Final security admission, frozen-candidate checks, version/RC choice and publication remain separate steps under the accepted roadmap.
