### 4.2 Internal seams and compatibility

All paths described as proposed below are predictions, not exact implementation commitments.
Keep `model/owlOntology.js` as the public facade and `internal/model/ontologyState.js` as snapshot/revision authority.
A proposed `internal/model/ontologyQueryIndex.js` may cache direct structural indexes by ontology identity and revision.
Benchmark the simple existing scan against lazy complete and selective indexes before fixing index cardinality.
Use iterative bounded traversal where depth is caller-controlled; do not multiply whole-graph walks under a new abstraction.

`internal/loading/managedOntologyIndex.js` remains the identity and resolved-import authority.
Closure membership must be read anew or invalidated by the manager's graph generation: a root's unchanged revision cannot validate a cache after an imported member changes or an import edge resolves differently.
Respect document-scoped anonymous identities and defensive returned collections.
Extract a common package-private closure reader only if profiles and queries genuinely share its semantics; a profile-specific assessment must not silently become a generic query scope policy.

Missing or inconclusive oracle output is an evidence gap.

External acquisition may be replaced with a counting/rejecting resolver at the genuine loader boundary.

Retain the existing benchmark corpus and resource budgets.

Use existing Jest deterministic/generated fixtures first.
Admit property or mutation tools only after current supported-version, reuse, license and integration research; `fast-check`, Stryker or a fuzz engine are candidates, not selected dependencies.
Every discovered counterexample becomes a deterministic regression.
If mutation testing is selected, review survivors on scope direction, annotation equality, transaction publication, profile rules, locality and escaping, with a measured ratchet and no invented percentage.
Keep extended campaigns distinct from each focused TDD run.

## 8. Release, adoption and recovery

The release sequence is:

1. Accept the exact selected member/adaptation/gate baseline, implement the slices and resolve applicable review/security findings.
2. Freeze integrated source, manifests, export/file inventory, oracle/fixture inputs, tool/runtime identities and active gate policy; reconcile every difference from published rc.1 and the intervening source changes.
3. Prepare exact `0.1.0-rc.2` metadata through the existing generators and version controls; changing the planning target alone changes no package version or completion flag.
4. Run the full mandatory producer qualification and retain one candidate tarball, SBOM, checksums, results and review record with fresh identities.
5. Obtain exact-artifact release approval covering publication and the policy-required channel updates, then use the existing protected release workflow and ordered human handoffs, retaining no-authority approval boundaries and one-attempt mutation/reconciliation rules.
6. Verify actual npm bytes/provenance, `next = latest = 0.1.0-rc.2` and immutable GitHub assets after publication; no consumer must accept in order to finish this producer release.
7. Offer exact-version documentation, migration notes and advisory results for optional consumer evaluation; stable `0.1.0` remains a later independently qualified producer release.

Do not declare rc.2 ready until all selected requirements and mandatory producer gates have current passing evidence and required decisions are resolved.
Do not infer stable readiness from rc.2 publication or relabel prepublication results as public-registry evidence.
The new feature programme precedes Phase 20 freeze; the existing restriction on adding feature families after that freeze still applies.
Any further public RC needs a concrete qualified change or observation need, not a ceremonial release per slice.

The producer release custodian observes aggregate producer gates, artifact identities, post-publication registry/asset verification and bounded compatibility reports.
