Date: 29 September 2026.
Status: implementation authorized on local `main` on 30 September 2026, with the specified configuration changes pre-approved and lengthy agentic reviews deferred to the final commit stage.
The owner separately approved the bounded Snapper 0.11.7 workaround during implementation.

**Goal:** provide reproducible Python formatting/linting and Markdown formatting/linting, reusing the strongest relevant tooling from the owner's repositories while preserving `owlapi`'s source, evidence, package, and CI contracts.

**Architecture:** retain Prettier and ESLint for their existing responsibilities; compose Prettier and Snapper for authored Markdown, add the official ESLint Markdown language plugin for content rules, and use Ruff for Python.
A small repository-owned adapter selects files and invokes pinned tools.
Standard Python dependency groups and a uv lockfile describe development tools only.

**Technology:** native JavaScript ES modules, the existing Jest runner, Prettier, ESLint with `@eslint/markdown`, Snapper, Ruff, uv, and CPython.
No new application language, build step, test framework, or runtime dependency is proposed.

**Specification and authority:** this plan records the requested tooling change.

## 1. Baseline and scope

### Existing coverage

The repository already formats Markdown through `prettier --check --ignore-unknown .` and its write counterpart.
It does not currently have a Markdown content linter or a semantic-line formatting stage.
ESLint currently checks JavaScript.
There is no Ruff configuration, Python dependency manifest/lockfile, or repository-wide Python formatting/linting command.
No tracked `.py`, `.pyi`, or `.ipynb` files were found at the inspected revision.
Python used by an evidence workflow is not equivalent to a Python source-quality policy.

The current toolchain includes Prettier `3.9.9`, ESLint `10.11.0`, Jest `30.5.2`, npm `12.1.0`, and the supported Node `22.23.3`/`24.21.0` lines.
Keep the Node support contract and existing JavaScript formatting output unchanged.

Markdown coverage must include root documentation, `docs/`, `.github/pull_request_template.md`, and `util/owlapi-reference/README.md`.
Do not copy Universal Ontology's narrower path roots and thereby lose `owlapi` coverage.
Preserve the existing exclusions for upstream material, fixtures, reconstructed history, and the two archived deep-review documents in `.prettierignore`.

`API.md` and `docs/compatibility/java-api-surface.md` are generated by `util/generate-java-api-surface.mjs`.
They require a separate ownership disposition from authored Markdown.
The generator currently applies Prettier internally and checks exact generated bytes.
Several Markdown files are shipped in the npm package; even layout-only edits can change candidate tarball bytes.

### Included work

- Deterministic setup, exact direct tool versions, lockfiles, and documented contributor commands.
- Python formatter and linter configuration that works when the repository contains zero Python source files.
- Authored Markdown formatting, content linting, file selection, and regression coverage.
- Explicit preservation of literal examples, rendered meaning, and generator-owned evidence.
- CI and release-workflow integration, exact job inventories, and receipt-reuse regression checks.
- One reviewed normalization of in-scope authored Markdown and the necessary developer documentation.

### Excluded work

- OWL parsing, public APIs, runtime dependencies, package exports, TypeScript, and application Python support.
- New documentation content, mass renaming, external-link crawling, spellchecking, or execution of code examples.
- Python type checking, complexity budgets, security lint rule suites, or notebook-specific product policy without actual consumers.
- Copying another repository's selective-CI implementation, changing the full-PR verification floor, or optimizing job duplication.
- Rewriting historical evidence, bypassing phase gates, changing branch protection, publishing a package, or merging this plan's implementation without the relevant authorization.

Distinguish installation from checking:

- An explicit setup command performs a locked sync of the `quality` and `prose` groups into the checkout environment.
- Check commands verify the lock with uv's native `--check` operation and invoke the already installed repository tools without automatic synchronization or interpreter download.
- Use offline mode for lock validation during checks; resolve and download only during explicit setup or an intentional dependency update.
- Missing or stale environments produce an actionable setup error; they do not cause `npx`, uv, pip, or a PATH executable to install a replacement behind the user's back.
- Check source/lockfile immutability.
  Tool caches may be written only to ignored cache locations; they are not verification evidence.

Use the native lock validator rather than parsing uv's lockfile with a repository-specific implementation.
The [uv synchronization documentation](https://docs.astral.sh/uv/concepts/projects/sync/) distinguishes locked validation from frozen execution; a frozen lock alone does not prove that it matches the manifest.
Ignore `.venv/` and any additional cache location actually used.
Apply those boundaries to ESLint and Jest discovery as well as Git, Prettier, Ruff, and the Markdown selector; installed tool files must never become first-party lint or test inputs.
Require available wheels during setup through uv's native no-build policy, and fail clearly if a selected host lacks a compatible distribution rather than compiling an unqualified fallback.
Do not create unused installation/cache directory conventions.

The selector must:

### 5.4 Authored Markdown formatting

Add Markdown-only Prettier overrides `proseWrap: "preserve"` and `embeddedLanguageFormatting: "off"`.
Retain the empty/default configuration for JavaScript and other existing Prettier file types.
Keep the existing blanket `[*] trim_trailing_whitespace = true` setting in `.editorconfig` unchanged, including for Markdown, as directed by the owner.
Do not add a Markdown exception to trailing-whitespace trimming.
Authored Markdown must express hard breaks without relying on trailing spaces; use the explicit backslash form defined by [CommonMark's hard-line-break rules](https://spec.commonmark.org/0.31.2/#hard-line-breaks).
Represent significant trailing spaces in authored code examples explicitly, such as through escaped string literals or annotated notation, instead of requiring those spaces to survive an editor save.
Review any existing space-based hard breaks during normalization and preserve their rendered meaning when changing their representation.
Test that the selected formatter pipeline and blanket editor trimming agree rather than repeatedly restoring and removing trailing whitespace.
The existing protection of generated, upstream, historical, and excluded fixture bytes remains in force; this policy does not authorize rewriting those files.
The [Prettier options](https://prettier.io/docs/options) and [EditorConfig property definitions](https://editorconfig.org/) explain these distinct responsibilities.

Add `.snapperrc.toml` with `format = "markdown"`, `max_width = 0`, and `clause_breaks = false`.
Use the native Markdown path, not Pandoc or an optional model-download path.
The policy is sentence-based semantic lines without arbitrary width wrapping or clause splitting.

For each selected document:

1. Read UTF-8 input and resolve Prettier configuration with EditorConfig enabled.
2. Apply Prettier layout, Snapper native Markdown formatting with the real stdin file path, then Prettier layout again.
3. Validate the final result through Snapper's independent JSON diagnostics, including diagnostics emitted with a successful process status.
4. In check mode, fail if bytes differ or a non-exempt semantic diagnostic remains; leave every source file untouched.
5. In write mode, validate proposed output before replacing that file and write only changed bytes.
   Report any partial batch completion if a later file fails; do not claim an all-file transaction.

Keep structural-content linting independently callable.
A formatting operation must not claim that rewriting layout resolves an unrelated missing link label or image alternative text.
Unexpected subprocess failures, malformed JSON, wrong per-file result cardinality, unknown diagnostic categories, and timeouts must be visible failures.
Use argument arrays, explicit UTF-8, finite output/time bounds, and checkout-local executables; avoid shell-built commands and ambient `snapper` lookup.
Only the specifically accepted version-bounded workaround may correct the reproduced upstream false positives.

The semantic oracle is preserved Markdown meaning, including code spans/fences, hard breaks, links, images, HTML blocks, lists, quotations, and tables.
[CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/) and the separately versioned [GitHub Flavored Markdown specification](https://github.github.com/gfm/) are the syntax authorities.
GitHub rendering extensions beyond that formal GFM version require explicit fixtures rather than a blanket claim of specification conformance.

### 5.5 Markdown linting with ESLint

Add exact development dependency `@eslint/markdown@8.0.3` and regenerate `package-lock.json` through the existing strict npm installation policy.
The inspected plugin supports the repository's Node versions.
Prove its integration with the actual installed ESLint version through native configuration inspection and real lint cases.

In `eslint.config.js`:

- Scope `js.configs.recommended` and the existing JavaScript rules explicitly to JavaScript before adding the Markdown language.
  The current unscoped recommended object must not accidentally apply JavaScript rules to Markdown ASTs.
- Apply the plugin's recommended content rules to Markdown and select `language: "markdown/gfm"` explicitly.
- Enable `markdown/table-column-count` for GFM tables.
- Keep raw HTML permitted; `markdown/no-html` is not part of this proposal.
- Do not enable the fenced-code processor or automatically execute/lint documentation examples as standalone programs.
- Preserve the existing shipped-source compatibility rules and JavaScript/Prettier relationship.

The [official plugin documentation](https://github.com/eslint/markdown/tree/v8.0.3) deliberately separates Markdown content rules from formatting and fenced-code processing.
It does not certify every document's rendered meaning or check that every external URL is reachable.
Qualify recommended rules against actual GitHub alerts, `<details>` blocks, explicit HTML anchors, mathematics where present, fragment links, and intentional examples.
Use a narrowly justified override only for a reproduced valid construct; do not disable whole recommended rule families to make the initial corpus pass.

Invoke ESLint's supported API over the selector's authored file list for `lint:md`.
Keep equivalent generated/history exclusions in the flat configuration for direct editor and CLI use, and test parity rather than allowing silent scope drift.
Use native `--print-config`/API inspection and diagnostic results instead of hand-validating a parallel ESLint configuration grammar.
