# Scope OwlAPI browser integrity checks to downloaded modules

**Implementation draft · 23 November 2026 · Owner-confirmed integrity decisions · HISEW R2 proposed**

Verify the OwlAPI tarball once with its trusted SHA-256 digest. Use browser tests to check the staged package’s behavior. Pin and verify the SHA-384 digest of every JSPM module the browser fixture downloads. Limit the import map’s `integrity` entries to these provider modules, including their mirrored URLs in the staged browser fixture. The owner confirmed these boundaries and the same-URL approval rule in DEC-004.

## Why change OwlAPI

| Bytes | From-scratch decision | Reason |
| --- | --- | --- |
| OwlAPI package and its same-origin fixture scripts | Verify the package at tarball admission. Bind the fixture sources to the qualification revision. | Git identifies the source revision. The candidate digest covers the complete release artifact. The package, fixture and import map are staged under the same trusted control. |
| JSPM modules downloaded over HTTPS | Review the exact versioned URL and SHA-384 digest for every direct and transitive module. Verify each response before mirroring it. | The provider can serve bytes independently of the Git revision. A committed expected digest gives the downloader an independent comparison. |

The HTML standard makes import-map integrity optional and lets a page specify a digest for any module URL in the graph. JSPM recommends generating integrity metadata for CDN modules, including static and dynamic dependencies. This plan applies that guidance to OwlAPI’s delivery path. If OwlAPI’s own modules are later delivered through a separately controlled service, or the fixture adopts an integrity policy that requires metadata for them, reconsider first-party browser SRI. [Git object model](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects.html) · [HTML import maps](https://html.spec.whatwg.org/multipage/webappapis.html#import-maps) · [W3C Subresource Integrity](https://www.w3.org/TR/sri/#introduction) · [JSPM integrity guidance](https://jspm.org/getting-started#import-map-integrity-for-security)

## Design decisions

1. **DEC-001 · Verify first-party bytes at tarball admission.** Owner confirmed. Keep the existing manifest and file digest owners, npm installation, package-identity check and fixture copying. Use the same verified candidate in focused and final runs. Bind fixture sources to the qualification revision. The first-party tarball check precedes npm and browser work. Behavioral checks cover the staged copy after unpacking.
2. **DEC-002 · Define the reviewed map at the existing generation boundary.** Reuse the locked and installed `@jspm/generator` 2.18.0 and stable serialization in `scripts/reference-import-map.mjs`. Its documented `integrity` option is a boolean. Keep native hashing and graph traversal. Validate normalized entries and omit recognized first-party paths when projecting the reviewed and runtime artifacts. JSPM can calculate local hashes internally during tracing. The persisted maps and their acceptance gates use only the provider pins. Carry an unrecognized or HTTP URL through validation and refuse it before projection. Retain `imports` and `scopes` and compare their full canonical contents along with the external pins. [Generator option](https://jspm.org/docs/generator/interfaces/GeneratorOptions.html#integrity) · [Repository lock](../../package-lock.json#L1750)
3. **DEC-003 · Verify against the admitted pins before staging.** In routine mode, require equality with the checked-in map before hydrating the mirror. Use the reviewed provider digests as the verification authority. Keep the upstream exact URL through verification, then rewrite it for the browser. Scope prefixes define resolution. Use the installed generator’s `link()` result to check that each provider URL in the static and dynamic dependency sets has an exact pin, alongside external mapping targets. Compare the trace, pins and original reviewed provider set on the first candidate before adopting this check. This covers transitive modules reached through relative imports. Use the existing verifier and mirror path validation. Preserve provider SRI during rewriting, when those previously external assets acquire relative URLs.
4. **DEC-004 · Retain the explicit refresh path and permit verified same-URL rebuilds.** Owner confirmed the exception conditions. Routine preparation rejects drift against the reviewed pin. For a legitimate rebuild at the same versioned URL, obtain independent evidence authenticating the exact replacement bytes. The evidence must bind the URL and SHA-384 digest to the authentic output. A fresh download and its generated digest record what JSPM served. Authenticity requires a separately trusted source. Obtain maintainer approval of the exact pin change, and retain the authentication evidence and approval with the candidate. Qualify the reviewed revision afresh against the replacement bytes before acceptance, including the three-engine browser suite. For deliberate updates, stage and verify the draft through `--write-reviewed-map` before touching the tracked map. Under single-writer checkout custody, recheck the starting map and publish the validated bytes by an atomic same-directory replacement. Preserve the original map on earlier failure and reconcile an interruption after replacement by comparing tracked bytes with the staged map. [Provider drift rule](../implementation-plan.md#246-decision-use-jspm-only-as-the-exact-pinned-reference-import-map-tool-and-provider)

The existing generator, downloader, browser loader and release runner each own a separate check. The required local change is a projection of the generated map and the review of its publication boundary. It uses the installed tool, its existing rights disposition and its locked dependency closure. Module hashes calculated from the same bytes under evaluation, a check limited to direct imports, or filtering integrity keys after mirroring would defeat the provider verification objective.

## Cutover, recovery and reconsideration

- **Cutover.** Land the projection and projected fixture together. Build the next proof against the integrated checkout. Keep `generatedSha256` defined as the digest of the exact generated map. Preserve prior evidence with its producing revision. The current repository search identified the browser manifest and provider inventory writers. Confirm any retained-artifact reader outside that tree before relying on cross-revision reuse.
- **Signals.** Use existing preparation errors and the candidate, map and provider evidence. A tarball mismatch identifies artifact admission. A map diff identifies graph or pin drift. A provider digest error identifies a byte verification failure. Capture the URL and expected and observed digests where appropriate. Publish a successful browser manifest only after preparation completes.
- **Abort and retry.** Stop qualification for unresolved graph, byte or provenance discrepancies. For a same-URL replacement, require the evidence and approval in DEC-004. Retain the failed observation and the prior receipt with its original provider pins. Use a fresh, isolated output directory after an interrupted preparation and retain the failed attempt per existing evidence policy. The maintainer checks statuses for all three browser lanes before accepting the cutover.
- **Rollback.** Before release, restore the previous generator and matching reviewed map together through a normal corrective source change. For a package whose local bytes differ from the restored map, regenerate the old-format map from that exact verified candidate and review its provider pins before retrying. Browser receipts from either form apply to their own candidate and producing logic. Any published artifact follows the established release recovery policy.
- **Reconsider.** Pause cutover if the installed generator omits a transitive provider module, a supported consumer requires same-origin integrity, or an evidence consumer requires the original map representation. First inspect an actual trace or receipt for that boundary. Keep the existing gate in place until the maintainer accepts an equivalent design. An ordinary OwlAPI edit that preserves the graph should stop producing reviewed-map diffs.
