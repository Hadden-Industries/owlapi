## 1. Purpose and authority

Give Node.js and browser users a reproducible, documented 0.1.0 package whose selected APIs behave according to an explicit Java 5.5.1-compatible or normative contract, with defensible performance comparisons and an operable release process.
Fewer CI minutes or favorable benchmark ratios are useful only when they preserve that result.

This is the current remaining-work roadmap.
The [original implementation plan](../implementation-plan.md) remains the historical architecture and decision record and currently supplies machine-parsed release requirements.
Its stale progress prose, old runtime numbers and old public-root counts must not be used to reconstruct today's backlog.
Its valid invariants remain: native ESM, Java-shaped public ownership, private RDF engines, exact artifacts, source/rights integrity, independent producer qualification and immutable release history.

The active [producer policy](../release/producer-release-policy.json), [producer gates](../release/producer-gates.json), [runtime policy](../release/runtime-policy.json), [API registry](../compatibility/java-api-surface.json) and profile decision ledger own their respective executable domains.
This planning document does not make an unimplemented gate change effective.
SLICE-002 reconciles those controls with the new roadmap before any release candidate is admitted.
Passing the old gate-registry consistency check establishes consistency with its current inputs, not 0.1.0 readiness.

WebVOWL and Universal Ontology adoption, deployment and sign-off remain independently owned and non-blocking for OwlAPI releases.
Producer-owned installed interfaces, representative corpus provenance, Java comparisons and browser/worker checks remain required.
Complete Java OWLAPI coverage, new parser families, reasoning, SWRL, public parser/storer registries, TypeScript declarations and upstream W3C reporting are not newly added to 0.1.0 by this reconciliation.

## 6. Performance parity qualification and repairs

Use the existing [performance plan](2026-10-28-remaining-java-api-performance-parity-implementation-plan.md), harness and evidence files as the starting point.
The ongoing task owns its edits and final delivery; this roadmap consumes its resulting candidate and residual ledger.
Its targeted-test instruction is not replaced by launching another full suite or benchmark concurrently here.
The future integrated release candidate still needs its applicable final producer qualification.

The current coverage file describes 70 grouped workloads, not exhaustive methods or overloads.
The process summary explicitly labels its three-process comparison as checksum-only screening.
The working results document reports favorable final targeted ratios while other retained report epochs still contain mismatches or unqualified rows.
Join those reports only by exact source, harness, fixture and runtime identities; never collapse them into one unsupported final pass.

Required acceptance is:

1. Map every release-relevant public member to a semantically admitted workload, a functional-only check with a justified performance disposition, or a visible gap.
   A class-level benchmark does not qualify every member; fast rows need semantic admission too.
2. Verify equivalent useful work before timing: fixture sizes, operation counts, setup/timed boundaries, eager/deferred evaluation, observable result consumption, ordering, lexical values, metadata, errors, mutations and reset state.
   Checksums/counts alone are insufficient; use independent structural/semantic sinks outside the timed loop.
3. Report both behavior profiles separately for every selected group.
   The retained target is JS/Java at most **1.10** for each comparable profile; an unresolved or incomparable case is not a pass.
   A necessary extra normative contract cost or measurement-resolution limit needs a precise, owner-accepted residual disposition rather than a false parity label.
4. Retain the established two warmups/five measured calls and at least three independent sequential JS processes for admitted comparisons, with control/candidate order and raw samples recorded.
   Repeat only when variance or a new change warrants it; keep profiling runs separate and avoid concurrent benchmark processes.
5. Evaluate cold process, first operation on a new snapshot, warm operations, mutation/query behavior and memory lifetime where affected.
   A first call inside an initialized suite is not process-cold, and a sampled heap delta is not retained or peak memory.
6. Preserve cancellation, finite resource checks, ordering, fresh public collections, iterator/override observations, target semantics and losslessness work.
   No new unbounded cache, eager/deferred shortcut or omitted validation is an acceptable optimization.
7. Bind evidence to final source and tool/dependency epochs.
   A refreshed dependency, changed fixture/sink, new JDK observation or semantic repair invalidates the relevant comparison until reassessed.
   Historical Java medians remain historical; no joint confidence interval is inferred without the underlying Java samples.

Optimization follows demonstrated hotspots and the existing ownership seams: immutable snapshots/read models, RDF read views, structural values, serializers, profile traversal and manager state.
Each repair needs a failing behavioral or performance observation, the smallest contract-preserving change, focused regressions and a new admitted measurement.
Only afterward aggregate the complete final coverage and remaining limitations.
