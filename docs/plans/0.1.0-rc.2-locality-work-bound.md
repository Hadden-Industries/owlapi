# rc.2 locality resource decision

Owner decision on 2026-10-09: "Does the Java API impose any limits? If it does not, we should not either (but a caller may set a custom limit)".
Inspection of `LocalityModuleExtractor` and `SyntacticLocalityModuleExtractor` at pinned Java revision `b61ebe2da83daceebb3e7ba7afbd2582c9240c33` confirms no numerical work, input-count, structural-depth or elapsed-time limit.
Locality therefore has **no default numerical cap**.
This supersedes the proposal below and the baseline's proposed reuse of structural/axiom ceilings for locality only.
Existing loader, storage, transform and profile defaults are unaffected.

Optional `maxWork`, `maxAxioms`, `maxDepth`, `maxAnnotationDepth` and `timeoutMs` accept nonnegative safe integers; omission or `null` disables that limit.
An explicit work limit covers every extraction phase and all STAR passes without resetting.
Exhaustion rejects with `ResourceLimitError` and never returns a partial module.
Options are captured before seed iterators and filters; cancellation applies throughout asynchronous extraction.
The synchronous constructor captures and validates its immutable axiom base without imposing a default size/depth cap.

## Superseded proposal and retained measurements

Propose **10,000,000 work units per extraction**, covering input capture/validation, filter calls, structural occurrences, signature/index edges, locality evaluations and all fixed-point/STAR passes.
No phase resets the counter.
Exhaustion rejects with `ResourceLimitError`; it never returns a partial module.
Add `maxWork` to the locality options, allowing nonnegative safe integers up to this ceiling so callers can lower it.
Values above the ceiling reject.
Capture options before invoking iterators or filters.
Abort and elapsed checks apply to all asynchronous phases.
