## Preserve a signed checkpoint

Each protected history ref is an owner-signed annotated tag named `owlapi-release-history/OPERATION` over a commit containing `evidence/checkpoint.json` and the original payload files. Pass its 40-character **tag object** to a dispatch. The index has `schemaVersion: 1`, `repository: "Hadden-Industries/owlapi"` and a `files` array of unique flat names, lengths in `bytes`, and hexadecimal SHA-256 values. Include only regular Git blobs. In `checkpoint.json`, retain the owner’s native `id`, `updated_at` and `bypass_actors` readback for the history rulesets in `rulesets`. The hosted reader checks the same live rule revision when GitHub omits bypass actors from its read-only response. The reader checks signer, protected live ref, exact tree inventory and every byte. Retain the Git objects and immutable assets in the existing off-platform backup. Credentials, private scanner details and OTPs do not belong in evidence.

The entire Git tree behind each history tag is public. Before creating or pushing it, review every blob and set `disclosure: "APPROVED_FOR_PUBLIC_GIT"` on the index and `disclosure: "PUBLIC"` on each entry. Keep restricted findings, identities, credentials and unredacted reports in owner-controlled private storage. Commit only release-safe evidence or a public signed disposition referencing a private digest. A release requiring restricted evidence bytes stays blocked until an approved public proof or confidential verification route exists. Filtering the eventual release archive cannot remove material already pushed to Git.

Use `owlapi-release-history/stage-N`, `labels-N` or `classification-N` under the same namespace for a writer, where N is the next native workflow run number. The job rechecks its own number and attempt. For every previous protected reservation include `reservation-KIND-N.json` with its tag object SHA in `object` and a resolved `state` (`SETTLED`, `REJECTED` or `RECONCILED_NO_PENDING_EFFECT`). Never settle an unresolved external effect. For a long-lived history, store prior dispositions together in the signed index’s `dispositions` object keyed by their original record filenames. Every matching protected ref still requires its own exact object and disposition. These refs survive removal of Actions history. A skipped run consumes its reservation. Owner-reviewed managed CodeQL analyses must be at most seven days old, and the stage writer rechecks them before submission.

Include `stage-intent.json` in the checkpoint with `commit`, `version`, original qualification `run` and `attempt` as strings, `manifestSha256`, `tarballSha256`, selected `channel`, `githubLatestBefore` for the GitHub latest release ID or null, `before` values for pilot/latest/next (null means absent), and accepted `rights` and `benchmark` dispositions. Supply the original dispositions of any preceding stages. Start `stage-release.yml` on the same protected SHA. It records a request before invoking npm and retains the stage ID and outcome.
2. In the owner's authenticated npm session, run `npm stage view STAGE_ID --json` and `npm stage download STAGE_ID`. Save the native view JSON and the original stage journal. Run `node scripts/staged-release.mjs verify-private MANIFEST MANIFEST_SHA256 JOURNAL VIEW_JSON DOWNLOADED_TGZ`. Save the output as `private-check.json` only on success. Compare scoped identity, tag, SHA-256 and npm integrity. Run the required installed-package checks against the private copy. Reject or investigate any mismatch before signing.
3. Sign the annotated `vVERSION` tag over that exact source and push it under the existing owner release procedure. Prepare a signed checkpoint containing the private proof, the three original candidate assets, and reviewed `release-notes.md`. Its `operation.json` binds `type: "draft"`, the original qualification `source` SHA, the reviewed protected `controller` SHA (if it changed, include `controller-delta.json` with the original `source`, `controller`, exact `git diff --no-renames --name-only` paths in order, and `decision: "OWNER_REVIEWED_CONTROL_ONLY"`), `version`, `qualificationRun`, `qualificationAttempt`, `manifestSha256`, `stageRun`, `stageAttempt`, `stageId`, `tagObject` and `expectedReleaseId: null`. Verify the exact three draft assets and record `draft.json`. After an interrupted creation, bind `expectedReleaseId` to the reconciled original ID before resuming the missing uploads. When resuming sealing, use the same signed checkpoint so the evidence archive reproduces its original digest.
4. From the reviewed controller checkout, set `GITHUB_SHA` to its commit, `GITHUB_REF=refs/heads/main`, `GITHUB_REPOSITORY=Hadden-Industries/owlapi`, a read-only `GH_TOKEN`, and `HISTORY_OBJECT` for a signed `before-approval` operation. Run `node scripts/staged-release-followup.mjs before-approval` within five minutes before approval. Repeat the check if its window expires. It reopens the draft and compares the npm labels and GitHub latest release to the stage intent. Preserve `.release/followup/before-approval.json` with its digest in `approval.preapprovalSha256`. Approve that same stage interactively with npm 2FA only after the draft readback. Preserve `approval.json` with `state: "APPROVED"`, `stageId`, `releaseId` and actual `approvedAt` UTC timestamp. An unresolved or rejected stage never authorizes a replacement submission.

Dispatch `release-registry.yml` with a signed `registry` operation and the original private proof, draft and approval. The approved stage's publisher identity is the origin of provenance. Anonymous registry reads qualify bytes, both install spellings and documentation. Each frozen Linux, Windows and macOS lane exercises the package using its consumer Node/npm pair. Submit the resulting `seal.json` in a checkpoint to `release-completion.yml`. It independently checks the immutable release, tag, all five asset digests and native GitHub release and asset attestations. Preserve that post-seal receipt in signed history. Completion reopens the original writer artifact and signed intent, verifies the exact published metadata, immutable ID, tag and five assets, and performs no provider writes.

## Change labels and complete support

When restoring a pre-staging RC, include its original attested release evidence file under its published name in the signed checkpoint. The channel workflow checks the original four assets, immutable release ID and annotated tag object against GitHub. Staged successors require their own `immutable-VERSION.json` completion records. Historical evidence supplies no fresh staging or publication approval.

After npm acknowledges a label write, the writer allows up to five minutes for the public tag map to converge. It polls only while the previous approved map is visible or a registry read is transiently unavailable. A conflicting value stops the operation immediately. If the deadline expires, retain the acknowledged journal and reconcile by reading the registry before scheduling any further write.

A signed `channel-operation.json` records a unique `operationId`, operation `type` (promote, preview, close-preview or withdraw), version, prior stable and preview line in `support`, complete guarded `before` and `after` tag maps, and `githubBefore` / `githubAfter` with prerelease flag and latest ID or null. Include the evidence described above for each selected release or restore target. A preview may explicitly `openLine`. Withdrawal supplies separate `{tag,target}` entries in `restore`.

Run `release-labels.yml` first. Check every affected tag and retain the request, acknowledgement and readback. Freeze the original operation bytes and retain the returned `runId` and controller `commit` in `label-origin.json`. Dispatch `release-classification.yml` with the same operation and select `github`, followed by `verify`. When GitHub classification changes, include the original `github` writer’s `runId`, `attempt` and controller `commit` in `classification-origin.json` so completion can check its acknowledged journal. Record the verified support and label values in `support-designation.json` when the operation completes. The pre-stable RC and promoted stable support designations have independent lifetimes. A lost acknowledgement, third registry value or conflicting prior request requires reconciliation in signed history. Never recreate a version or move a signed release tag to repair publication.

If the original 30-minute availability window has expired, a later read-only registry dispatch makes one bounded observation and records the missed window. Confirming current availability does not establish when the package first became available. For a defective stable with a qualified predecessor, the signed withdrawal restores both npm’s default and GitHub’s latest ID. A first stable with no predecessor can remove the npm default while its GitHub designation remains explicitly guarded.
