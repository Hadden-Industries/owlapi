## Contradictions and statements open to conflicting readings

**1. An abandoned alpha has no valid publication mode.** §17.26.3's failure branch says that a correction required after tag creation but before a successful registry write means abandoning `0.1.0-alpha.0` and preparing `0.1.0-alpha.1`. But §2.60's mode table assigns `DIRECT_BOOTSTRAP` specifically to "the still-absent `owlapi@0.1.0-alpha.0` package" and `OIDC_STAGED` to "every later release" — while that same section states the bootstrap path exists because "npm cannot stage a package that does not yet exist." After a pre-write abandonment, `owlapi` still doesn't exist on npm, so `0.1.0-alpha.1` literally cannot use `OIDC_STAGED`, yet the table's wording excludes it from `DIRECT_BOOTSTRAP`. The mode selector needs to key on *package existence*, not on the literal version string.

**2. "The maintained WebVOWL branch" is never defined, and may be the branch that must not change.** §17.26.1 requires the `feature/ui-ux-enhancements` remote branch to "remain unchanged as reconstruction evidence until all extracted/replayed histories pass their gates," with UI/UX work replayed onto "a separately named branch." But §17.26.4 and §2.10.3 then apply the consumer cutover to "the maintained WebVOWL branch" without ever saying which branch that is, when the reconstructed branch takes over, or when the frozen original is released. As written, the cutover target is either the frozen branch (contradiction) or an undefined one.

**3. Node 26 in §17.27.1.1.** The section says "Keep `engines.node` exactly `^22.0.0 || ^24.0.0`" and then, two sentences later, "If Node 26 has become LTS by this gate… make it blocking only after all package, retained-tarball and WebVOWL-consumer gates pass." Making Node 26 blocking necessarily changes `engines.node`. Given Node 26's expected LTS promotion around October 2026, this branch is likely live rather than hypothetical — and if it activates, the §17.26.1.2 governance test that rejects promoting "Node 26 Current" to `SUPPORTED` also becomes stale terminology.

**4. Full-history checkout scope.** §17.26.1 states that "only the release source/tag-verification job checks out the captured `github.sha` and fetches complete history/tags." But step 5 of the deterministic gate describes the *packing* job as checked out through the "captured-SHA/full-history/no-persisted-credentials policy." Either the packing job also fetches full history (contradicting "only"), or step 5 is naming a policy bundle whose full-history element doesn't apply — which isn't stated.

**5. CommonJS conversion: permitted or a failure?** §2.46 and §17.26.1.2 require the import-map gate to "fail on… a CommonJS/UMD execution leak," while the same subsection instructs implementers to "let the approved ESM provider perform any reference-consumer CommonJS conversion." Since `rdfxml-streaming-parser` is explicitly identified as "the CommonJS RDF/XML implementation boundary," the gate will encounter provider-converted CJS by design. The line between permitted provider-side conversion and a prohibited leak is never defined, so the gate is unimplementable as specified.

**6. §2.29 is never cited in either phase.** Phase 19's completion gate enumerates §§2.30–2.61 essentially exhaustively but omits §2.29 (distribution tags as release channels) and §2.33 (bad-release recovery) — even though §2.29 is the governing decision for the `next`/`latest` behavior both phases implement, and §2.33 is invoked by name in §17.26.3 and §17.27.5. A reader checking completion against the enumerated list would not verify §2.29 at all.

**7. Step 16 presents a mode choice Phase 19 cannot make.** The deterministic gate's step 16 gives parallel instructions "for `DIRECT_BOOTSTRAP`" and "for `OIDC_STAGED`," implying either could govern the alpha. §17.26.3 mandates the bootstrap token path, and trusted-publisher configuration is explicitly deferred until "after the alpha and immutable-release checks pass." The `OIDC_STAGED` half of step 16 is unreachable in this phase.

**8. Two `latest`-related checks that only reconcile through a failure.** §17.26.4 requires both "no latest tag exists" and "bare npm install owlapi does not silently select the prerelease." With no `latest` tag, `npm install owlapi` doesn't quietly do the right thing — it errors (`ETARGET`/`ENOVERSIONS`, the same codes §2.10.1 recorded from its probes). The check passes, but by way of a broken install path that the README (`npm install owlapi@next`) never documents.

## Risks the document doesn't appear to address

**9. `git-filter-repo` cannot split a commit into several commits.** §17.26.1 requires `MIXED_REQUIRES_SPLIT` commits to be partitioned so that "a split result may map one original commit to an `owlapi` commit, a clean WebVOWL UI/UX replay commit and/or a WebVOWL integration replay commit" — and simultaneously requires retaining "the tool-generated original-to-rewritten commit map as repository provenance." `git-filter-repo`'s commit map is 1:1 (or old→zeros for dropped commits); it has no representation for 1:N. Splitting requires interactive replay or custom callbacks, and the resulting provenance map has to be hand-maintained. Neither the tool gap nor the map's expressiveness limit is acknowledged.

**10. Registry-side dist-tag behavior on first publish is treated as controllable.** §2.29 asserts that "prerelease publication **MUST NOT** create or move `latest`," and §17.26.4 makes "no latest tag exists" a mandatory gate. If the registry assigns `latest` on a first-ever publish regardless of `--tag next`, Phase 19 cannot complete, and no corrective operation is authorized anywhere in the phase (Phase 20 authorizes `npm dist-tag rm … next`; §2.33 authorizes removing `latest`; Phase 19 authorizes neither). The same exposure recurs in Phase 20 at the first RC, against "Never create or move `latest` for a release candidate." Worth a pre-flight determination and an authorized remedy.

**11. The frozen browser ceiling is enforced against code the project can't change.** §2.20 applies the dated ceiling to "the complete reachable production graph, including lazily loaded RDF/XML, N3-family, JSON-LD and XML fallback paths," and §17.27.1.1 forbids satisfying the check "by adding package transpilation or a polyfill." Those paths are exact-pinned third-party bytes (`jsonld@9.0.0`, `n3@2.3.0`, `rdfxml-streaming-parser@3.3.0`, `@xmldom/xmldom@0.9.12`). If any ships syntax newer than the freeze date, there is no permitted remedy — not transpiling, not polyfilling, and not upgrading (which would need a new RC and could reintroduce the same problem). No escape branch is defined.

**12. A moving Browserslist query inside an immutable published artefact.** §17.26.4 requires "exact agreement among `engines`, the alpha browser query, the README's §2.22 environment statuses, CI matrix and recorded required/extended results." `baseline widely available` resolves differently over time, so the packed, immutable alpha's README support claim drifts away from what its own manifest query resolves to for a consumer installing months later. §2.20 justifies the moving query for development but doesn't address the published-artefact consequence.

**13. Deep imports into dependencies may not survive those packages' own `exports` maps.** §17.26.1.1 records that the adapters lazily load `n3/browser/n3.min.js` and `jsonld/dist/jsonld.esm.js`. Both are deep subpaths, and their resolvability depends entirely on whether `n3` and `jsonld` export them. The phase anticipates exactly one of these ("the initial native-map test is expected to expose the selected N3 UMD deep path") but not the `jsonld` case, and the plan's own rule that consumers must never deep-import `owlapi` isn't mirrored by any constraint on `owlapi` deep-importing its dependencies. It's also a silent upgrade hazard for Phase 20 and beyond.

**14. The import-map closure will pull Node-builtin shims.** `rdfxml-streaming-parser` is stream-based. Tracing the "static and statically analyzable literal dynamic-import closure" through JSPM will resolve `stream`/`events`/`buffer` to provider polyfills, all of which must then be hydrated into the local mirror with integrity metadata and counted against the §17.26.2 "initial and lazy browser bundle sizes against the approved budgets." §17.26.1.1's claim that the graph has "no direct dependency on Node built-ins" is true as written but doesn't cover the transitive case, and nothing sizes or approves the shim closure.

**15. The isolated WebVOWL trial can pass without exercising owlapi's real closure.** §17.26.2 step 11 runs WebVOWL's existing clean install *before* applying the cutover patch, then installs the tarball "with no save and no lockfile mutation." At that point WebVOWL still declares the same six runtime packages itself; npm will hoist and dedupe, so the trial may resolve `n3`, `jsonld`, etc. from WebVOWL's tree rather than owlapi's declared exact pins — and version skew would nest silently rather than fail. The dependency-removal audit that would expose this happens later (§17.26.4). Separately, `--no-save` alone does not prevent lockfile writes; `--no-package-lock` is needed and isn't named.

**16. Namespace deadlock has no terminal off-ramp.** §17.26.4 states that "if npm namespace control remains unresolved, the phase is blocked rather than renamed or reported complete," and §17.26.3's namespace branch ends at "contact npm Support." Because the `owlapi` name is baked into §2.10, the manifest, README, repository identity, and Phase 20's completion criteria, an unresolvable namespace outcome blocks the plan permanently with no decision procedure, no time bound, and no authorized alternative. Given that §2.10.1's evidence shows the name in an unpublished-but-existing state (`ENOVERSIONS` implies a surviving package document, likely still owned), this is a live risk rather than a remote one.

**17. Smaller operational items.** (a) §17.26.3's preflight runs `npm publish --dry-run --provenance` in a job described as read-only; provenance generation needs `id-token: write`, which §17.26.1 grants only to the npm job — verify the dry run doesn't fail or silently skip provenance validation. (b) §17.26.4 enables "2FA for package changes" *before* configuring the OIDC trusted publisher; depending on which npm 2FA mode is selected, that ordering can block the automated stage write the next release depends on. (c) The whole `OIDC_STAGED` path assumes `npm stage publish/view/download/approve` semantics — in particular that a staged tarball downloads byte-identically and that approval preserves the fixed tag. If staging normalizes or re-signs bytes, the SHA-256 equality gate in §17.27.4 fails with no fallback. (d) Phase 20's duration is unbounded while maintained WebVOWL stays pinned to the alpha, so any defect Phase 20 is fixing stays in WebVOWL production for the whole phase; no interim bump is contemplated.
